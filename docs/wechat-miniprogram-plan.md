## 1. 文档用途与决策边界

记录本次讨论中用户明确确认的方向、技术可行性研究和候选业务场景，供未来小程序开发使用。本文不是小程序功能已经完成或外部集成已经验证的声明。

- “已确认”是本阶段的产品与架构依据。
- “建议”是讨论中的方案，仍需在实施前确定范围。
- “待验证”涉及平台规则、服务接入、网络或数据处理条件，不得当作已通过的上线条件。
- 本文补充 V2 规格；双前端、账号隔离与积分会员方面，以本文记录的最新决定为准。其余产品定位和工程要求继续沿用原规格。

## 2. 已确认的方向

| 事项 | 决定 |
| --- | --- |
| 产品形态 | 两个前端：现有 Web 和后续微信小程序 |
| Web 市场 | 主要面向海外用户；用户希望国内用户也能使用，实际服务范围仍需满足供应商和数据处理条件 |
| 小程序市场 | 主要面向国内用户 |
| 小程序名称 | NewSelf发型设计；正式可用性需通过微信名称检查及审核 |
| 企业主体 | 计划使用企业主体申请小程序账号；申请流程研究按中国大陆企业主体说明，实际主体资料待准备 |
| 共用后端 | 指共用同一个 Convex 部署中的数据库与核心业务函数，并非仅共享代码 |
| 账号关系 | 第一阶段微信用户与 Web 用户视为两个独立用户，不要求绑定，不提供自动合并 |
| 积分与会员 | 可以共用业务系统；各用户余额、会员权益和订单独立，不跨端互通个人权益 |
| 收费安排 | 积分和会员是未来可能采用的收费方式；价格、套餐、支付供应商与上线时间尚未确定 |
| 当前工作范围 | 记录规划；不因此实施小程序、支付、账号绑定或后端迁移 |

两端都保持 newself 的核心定位：AI 发型顾问和发型决策系统。核心流程仍为：

`自拍 → 脸型与头发分析 → 推荐 → 发型试戴 → 现实可实现性 → 理发师指南`

结果应保持人物身份，并帮助用户与真实理发师沟通可执行的方案。

## 3. 同一个 Convex 的接入方案

### 3.1 可行性与边界

Convex 提供公开函数 HTTP API，小程序可使用 HTTPS 请求调用 query、mutation 和 action，也可以调用在 Convex 中定义的 HTTP Actions。[官方 HTTP API](https://docs.convex.dev/http-api/)、[HTTP Actions](https://docs.convex.dev/functions/http-actions)

| 方式 | 接口地址形式 | 用途 |
| --- | --- | --- |
| 标准 HTTP API | `https://<deployment>.convex.cloud/api/query`、`/api/mutation`、`/api/action` | 调用公开业务函数 |
| 自定义 HTTP Actions | `https://<deployment>.convex.site/<path>` | 提供登录、任务、积分等业务接口，并调用核心函数 |

建议先为小程序提供一组清楚的 HTTP 接口，内部复用同一个 Convex 的业务逻辑；Web 保留现有接法。最终采用标准 API 还是自定义接口，留待接入验证后确定。

普通 HTTP 请求不会自动获得 Web 的实时订阅能力。建议第一版通过任务编号查询生成状态，支持离开页面后回来继续查看；是否增加小程序 WebSocket 接入另行评估。V2 规格中的“不需要 polling”描述针对原 Web 实时客户端，不是小程序接入的限制。

生成应由后台任务执行，避免依赖用户一直停留在前台。提交、重试和查询需要避免重复创建任务或重复扣积分。

### 3.2 身份认证与用户隔离

Web 继续使用 Clerk。小程序建议采用微信登录，并在服务端验证临时登录凭证后建立自己的用户会话；微信登录凭证不是 Convex JWT，不能直接交给 Convex 当作用户令牌。

Convex 支持自定义 JWT 验证，为接入微信身份提供技术基础；令牌签发、刷新、撤销和验证方案尚未实现。[Custom JWT Provider](https://docs.convex.dev/auth/advanced/custom-jwt)

建议的身份流程：

`微信登录 → 服务端向微信验证 → 查找/创建内部 userId → 签发短期会话令牌 → 调用受保护接口`

- 内部统一使用 `userId` 标识用户，并记录所属身份来源。
- 微信身份需要结合应用身份识别，不能假设不同小程序的 openid 可以直接通用。
- 即使现实中是同一个人，Clerk 身份与微信身份也创建两个独立账户。
- 不按姓名、头像或照片自动合并用户；不因跨端绑定要求增加手机号采集。
- 每个接口在后端验证身份和资源归属，不能信任客户端传入的 userId 或 openid。
- 用户 A 不能读取或消费用户 B 的照片、结果、积分或会员权益。
- Clerk secret、微信 AppSecret、JWT 签名私钥、Convex 管理密钥和其他服务密钥只保存在服务端，不进入小程序包或公开配置。

未来如增加自愿账号关联，需要另行设计身份验证、余额合并、会员冲突和订单退款规则，当前不预先实现。

### 3.3 共用范围与可分开配置的服务

共用发型库、推荐规则、提示词版本、生成任务管理、积分流水、会员校验和成本记录等核心能力。自拍、生成结果、收藏、理发指南、余额、会员和订单均按独立 userId 隔离。

同一个 Convex 不要求所有前端使用同一个 AI 供应商或对象存储。可以按业务场景选择服务，AI 集成继续置于 `ImageEditProvider` 后面。国内模型和存储服务尚未选定，现有 Web 的 GPT Image 与私有 R2 决定不因此被替换。

小程序直连 Convex 的正式域名配置、国内网络表现和数据处理要求尚未验证。必要时可评估自己的 API 网关，后面仍使用同一个 Convex；增加网关不会自动消除数据跨境问题。若条件不满足，应重新讨论部署选择，不能声称共用 Convex 已具备上线可行性。

## 4. 积分与会员规划

共用系统、独立权益是已确认原则。例如，同一个人在 Web 购买积分，不会出现在其微信账户中；微信会员也不会自动使 Web 账号成为会员。

以下为未来实现建议，尚未确定具体收费产品：

- 会员提供功能权益和周期额度；积分用于消耗 AI 成本的生成操作。
- 充值积分、会员赠送积分和活动积分分别记录来源、有效期及变动流水。
- 在 Convex 中统一完成额度校验和原子扣减，避免两端或并发请求各自修改余额。
- 支付回调、会员额度发放、任务重试和失败返还均需幂等处理。
- 订单记录渠道、币种、金额及外部交易标识，供退款和核对使用。
- 国内与海外可采用不同价格和支付渠道，但各自购买结果归属各自账户。
- 会员续费、取消、额度过期、失败返还与退款规则需在实现前明确。

支付继续保持抽象，供应商与平台规则确认前不实现 checkout。原规格中的价格示例不构成此次讨论确定的套餐。

## 5. 用户使用与传播场景

### 5.1 用户提出的传播方向

发型结果具有分享动机：用户可以用“你看这个发型适不适合我”向朋友、朋友圈或家族群征求意见，形成自然传播。

### 5.2 建议优先验证：请朋友帮我选

候选流程：选择 2–3 个结果 → 预览分享内容 → 发给好友/群 → 朋友查看或选择 → 用户查看意见 → 接收者可开始自己的试戴。

“周末准备剪头发，A 还是 B？”可以作为分享文案示例。投票功能是建议，尚未批准为第一版必做。若采用，建议先做有限选项，暂不开放文字评论。

分享出口分别考虑好友/群卡片、朋友圈页面和保存图片海报。朋友圈单页模式存在接口限制，分享落地页应先展示内容；平台能力与 iOS、Android 兼容性需真机验证。[腾讯云开发分享说明](https://docs.cloudbase.net/recipes/add-share-with-params-miniprogram)

建议的分享约束：

- 结果默认私有，用户主动选择要公开的图；生成授权与分享授权分开。
- 分享使用独立凭证，支持撤销和有效期，不把原始自拍签名链接当成长期分享链接。
- 分享页仅展示获准公开的内容，不暴露完整个人资料或其他私有结果。
- 用户撤销后，应用可关闭在线分享页，但不能撤回接收者已经保存或转发的图片。
- 保留适用的 AI 生成内容标识。
- 建议先依靠内容和决策价值传播，不将强制分享、分享次数奖励或邀请返积分作为默认需求。

可观察分享进入、开始试戴、完成生成和打开理发指南等转化。不得把用户点击分享按钮等同于分享成功。

### 5.3 其他候选业务场景

| 场景 | 用户价值 | 阶段建议 |
| --- | --- | --- |
| 短发、刘海、卷发决策 | 剪之前比较变化，减少犹豫 | 核心流程 |
| 参考照片试戴 | 预览喜欢的发型，并解释现实差距 | 复用现有参考图方向 |
| 面试、婚礼、毕业照 | 按场合和打理时间选择 | 后续验证 |
| 陪父母选发型 | 在本人同意下试戴、家庭讨论 | 后续验证 |
| 理发前沟通 | 给理发师看效果图和具体要求 | 核心差异化 |
| 理发后复盘 | 用户主动保存实际结果与反馈 | 后续验证 |
| 门店扫码咨询 | 顾客试戴，理发师确认可执行性 | 少量门店试点 |
| 门店工具订阅或咨询套餐 | 将决策与服务连接 | 后续商业验证 |

上述场景是候选池，不意味着同时建设社区、门店交易、预约、排名或分销系统。

## 6. 企业账号、备案与上线准备

### 6.1 申请流程

计划路径：进入[微信公众平台](https://mp.weixin.qq.com/) → 注册小程序 → 选择企业主体 → 激活邮箱 → 填写主体与管理员信息 → 按后台提示完成验证及微信认证。[腾讯官方注册指引](https://cloud.tencent.com/document/product/1598/80508)

准备企业营业执照、统一社会信用代码、法人及管理员资料、公司控制的邮箱、联系方式，以及后台要求的对公账户或授权材料。管理员账号由公司掌握，开发人员通过成员权限加入。

填写名称“NewSelf发型设计”、头像、简介和客服信息。候选简介为“上传自拍，发现适合自己的发型，预览换发型效果，获得理发沟通指南”。名称、服务类目及资质要求以实际后台审核为准；认证费用、年审和办理时长未在本次研究中确认为现行固定值。

### 6.2 备案结论

面向国内用户运营的小程序需要先完成小程序备案再正式提供服务，境外 Convex 后端不能免除小程序备案。通过微信平台向企业所在地的通信管理局提交。[通信管理局说明](https://shxca.miit.gov.cn/xxgk/xyjd/wzba/art/2024/art_6ec21446e9ff4420a1bc620451f67fba.html)

需要分别处理：

| 事项 | 作用 |
| --- | --- |
| 微信认证 | 企业身份认证 |
| 小程序备案 | 主体与应用信息登记 |
| 网站/服务域名备案及微信域名配置 | 按实际服务部署与平台要求处理，不由小程序备案自动代替 |
| AI 应用登记/备案评估 | 按 AI 功能和属地要求另行确认，不由上述手续自动代替 |

工信部说明：通信管理局收到完整准确材料后，在二十个工作日内办理备案；材料准备、平台核验和补正时间不包含在该期限内。[工信部说明](https://www.miit.gov.cn/jgsj/xgj/hlwgl/art/2023/art_564bf0759d7e41d5b4aa8ce4996b9e84.html)

官方备案表将小程序的域名列表、服务器所在地和 IP 等网络接入信息标为无需填写。因此，办理小程序备案本身不等于必须先买国内服务器；调用 Convex 的网络与域名条件仍需另外验证。[官方登记表](https://xzca.miit.gov.cn/bsfw/bszn/art/2024/art_5d3cc7f452c04fdd97b6881a20b656f9.html)

### 6.3 AI、图片与隐私条件

研究日期为 2026-10-01；上线前应重新核实规则及服务条款。

- OpenAI 当前 API 支持地区名单不含中国大陆，并涉及在不支持地区访问或提供服务。不能以“海外服务器调用 GPT Image”作为国内服务条件已满足的依据；Web 服务国内用户的设想也需评估。[OpenAI 官方说明](https://developers.openai.com/api/docs/supported-countries)
- 国内图像编辑模型建议按人物一致性、发型准确度、耗时、失败率和成本进行对照测试；供应商尚未选择。
- 调用已备案模型的 AI 应用仍需结合功能与属地要求确认应用登记路径，并公示适用模型信息。[网信办公告](https://www.cac.gov.cn/2026-09/14/c_1791136833136332.htm)
- 展示、分享与导出应落实适用的显式、隐式生成内容标识，不能仅用品牌水印代替。[标识办法](https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm)
- 说明自拍用途、AI 接收方、保存期限与删除方式；涉及生物识别和跨境提供个人信息时，需确认单独同意及其他适用条件，不能仅凭通用隐私勾选框认定完成合规。[个人信息保护法](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)
- 国内存储与网关不会自动解决所有跨境问题；同一个 Convex 中的数据范围也需评估。
- 小程序上传需要单独适配。R2 支持预签名 PUT，不支持 POST 表单上传；预签名 URL 不能直接换成自定义域名。现有浏览器流程不能未经验证就复制到小程序。[R2 官方文档](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)

## 7. 开发、调试与发布建议

小程序前端技术栈尚未确定。Taro + React + TypeScript 是候选，便于延续现有技术习惯；可共享类型和业务规则，但 Next.js 页面、浏览器组件和 Clerk 界面需要适配或重写。[Taro 文档](https://docs.taro.zone/docs/3.x/GETTING-STARTED)

建议流程：

1. 注册企业账号，检查名称与服务类目，启动备案和相关材料准备。
2. 确定国内 AI、数据处理范围、存储与域名接入条件。
3. 取得 AppID，添加开发者，安装微信开发者工具，创建前端项目。
4. 优先验证微信登录与一次受保护 Convex API 调用，再验证上传、任务、结果读取。
5. 连接隔离的测试环境，在模拟器及真机调试，不把测试订单或额度写入生产。
6. 覆盖 iOS/Android、Wi-Fi/移动网络、授权拒绝、上传失败、重复提交、切后台恢复任务，以及分享落地页。
7. 上传代码并设置体验版，开启正式域名校验后邀请少量真实用户和理发师体验。
8. 部署生产后端，完成备案、隐私与 AI 材料，提交微信审核。
9. 审核通过后正式发布，观察耗时、成功率、成本及分享转化。

小程序代码上传、体验版、审核和发布与后端部署是不同环节。[腾讯发布流程说明](https://cloud.tencent.com/document/product/1301/55140)

建议的首版用户主线是“准备换发型 → 试方案 → 请朋友帮选 → 带指南去理发”。自拍、中文推荐、试戴、保存、分享及指南的具体范围仍需确定；投票、会员、支付和门店服务不能因记录本讨论而自动进入必做列表。

## 8. 开发前待确定/待验证清单

- 企业实际主体、管理员、名称可用性、服务类目及所需资质。
- 微信认证、小程序备案、AI 应用登记等实际办理路径。
- 小程序直连同一个 Convex 的域名配置和国内真机网络表现；是否需要网关。
- 微信会话与 Convex 鉴权接入，以及跨来源用户隔离测试。
- 满足隐私要求的数据范围、存储位置、删除和保存期限设计。
- 国内 AI 供应商、人物保持效果与成本；上传及结果下载方案。
- 原 Web 流程真实自拍端到端验证、后台任务和生产部署状态。
- 小程序框架、首版功能、分享渠道、是否采用投票与衡量指标。
- 未来积分与会员规则、支付供应商、退款和平台限制。

后续开发应先读取本文和当前状态，区分已有实现与未来方案，并在验证完成后更新结论和证据。现阶段不进行账号绑定、不互通个人权益、不默认拆分 Convex，也不宣称微信、支付或国内 AI 集成已经可用。
